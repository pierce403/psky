01 / The idea

One protocol.
Another foundation.

Farcaster identity. ATProto interoperability. Snapchain persistence.

PurpleSky proposes an ATProto PDS implementation backed by Hypersnap/Snapchain. It explores what happens when one decentralized protocol consumes another as infrastructure.

This is protocol composition, not a service that copies Farcaster posts into a second social graph. PurpleSky would publish native ATProto records from its backing state. Clients, relays, and AppViews see an ordinary PDS.

One social graph, multiple storage substrates.

02 / Architecture

The boundary is the design.

Everything beyond the PDS speaks ATProto.
Everything behind it is an implementation choice.

Inside

Snapchain mutations would be the source of truth; local repository blocks and indexes would be materialized views.

Outside

A normal DID, independently verifiable repo commits, standard records, and ordinary synchronization.

Still to prove

Mutation support, ordering, retention, and replay on the chosen Hypersnap network. No arbitrary event-log capability is assumed.

The compatibility claim is a design constraint to test. A full PDS also needs standard client auth, discovery, account lifecycle, blob handling, and operational behavior. No modification to ATProto itself is proposed.

Illustrative mapping. The FID ↔ DID proof format, wallet-only accounts, and account recovery are still open design decisions.

Farcaster/ETH authenticates and authorizes the account. A separate ATProto repo signing key produces standard commits. Key custody, rotation, and DID recovery authority must be designed explicitly.

Use a currently interoperable ATProto DID mechanism, preferably did:plc; do not introduce did:farcaster. Wallet sign-in would live behind the PDS’s standard client authorization flow.

03Longer-term question

Shared native
protocol objects

Could one user-signed social operation be meaningful to both protocols directly?

Signed social operation
FarcasterATProto

Do not start here. Identity, signing, repository, and message semantics differ today.

Inside Level 2: what would be persisted?

Conceptual operations, not a defined Snapchain wire format:

create app.bsky.feed.post/abc
update app.bsky.actor.profile/self
create app.bsky.graph.follow/xyz
delete app.bsky.feed.post/old

The event envelope would need record content, stable keys, authorization, ordering, timestamps, and versioned projection rules. The adapter must first establish how the chosen network accepts and retains these operations.

Identical records can reproduce the MST root. Identical signed commits additionally require fixed commit metadata and a signing strategy or retained signed commit bytes. Replay alone does not recover private signing keys.

Pruning, deletion, snapshots, media availability, and migration need explicit policies before this can be a durable source of truth.

07 / First proof

Small enough to prove.

All milestones proposed
  1. 01

    One identity

    1 FID ↔ 1 DID
    Farcaster / ETH login

  2. 02

    One mutation log

    Snapchain persistence
    Profile · post · follow

  3. 03

    One valid repo

    Records → MST
    Standard repo signature

  4. 04

    One consumer

    getRepo + subscribeRepos
    Unmodified ATProto reader

The acceptance test
If an unmodified ATProto relay/AppView can consume and verify a PurpleSky repository, the abstraction is working.

The first meaningful proof: a post originating from state persisted through Snapchain appears and verifies correctly in an unmodified ATProto consumer/AppView.

First prove the adapter can persist and replay the required operations. Then publish through com.atproto.sync.getRepo and com.atproto.sync.subscribeRepos, test restart/replay and stream resumption, and verify with existing software. Public AppView indexing also depends on discovery and service policies.

08 / Open research

The interesting questions
are still open.

These are design decisions to investigate, not capabilities already delivered.

  1. What should be canonical: Snapchain mutations or ATProto blocks?
  2. How should an FID ↔ DID binding be represented and proven?
  3. Who controls and rotates the ATProto repo signing key?
  4. Can repository reconstruction from Snapchain be fully deterministic?
  5. How should conflicting or concurrent mutations be resolved?
  1. How much Farcaster-native data fits existing Lexicons directly?
  2. What recovery path exists if PurpleSky disappears?
  3. Can an account migrate to an ordinary PDS while retaining its DID and repository?
  4. Could the same substrate expose both Farcaster-native and ATProto-native views?
  5. Which Hypersnap network, mutation format, and retention policy can support this?
