01 / The idea

One protocol.
Another foundation.

Farcaster identity. ATProto interoperability. Snapchain persistence.

PurpleSky proposes a distributed ATProto PDS implementation backed by Hypersnap/Snapchain. It explores what happens when one decentralized protocol consumes another as infrastructure.

This is protocol composition, not a service that copies Farcaster posts into a second social graph. PurpleSky would publish native ATProto records from its backing state. Clients, relays, and AppViews see an ordinary PDS.

One social graph, multiple storage substrates.

02 / Architecture

One logical PDS.
Many replaceable nodes.

The network is the backend.
ATProto remains the interface.

Service identity

A stable logical PDS endpoint in the DID document. Routing between workers does not change the DID or its advertised PDS.

Replaceable nodes

Stateless or mostly materialized gateways. A healthy, authorized, caught-up node should authenticate the user, accept writes, reconstruct the repo, and serve standard APIs.

Shared substrate

Canonical persistence and ordering come from the chosen network. Mutation admission, finality, retention, and recovery still require proof.

03 / Distributed state

Any node. Same repository.

The network is the PDS.

Precisely: PurpleSky presents a single logical PDS to ATProto while distributing its implementation across many nodes backed by shared Snapchain state.

Hosted PDS deployments can assign accounts to particular backends or shards. PurpleSky’s proposed authority is the shared substrate. A node is neither the identity authority nor the durable home of a repository.

The distributed invariantOne authoritative repository lineage per DID.

Users migrate onto the PurpleSky logical PDS. Switching PurpleSky workers is routing or failover, not account migration.

Concurrent requests. A single history.

If A receives “follow Bob” while B receives “post Hello,” both submit to the same ordering layer. Neither publishes an independently chosen repo head.

Concurrency, finality, and failover: what still needs to be specified?

Define ordering within each DID, commit boundaries, stable record keys, monotonic revisions, idempotency keys, retry behavior, and conflict/precondition handling. An accepted request must not become two commits when retried at another worker.

Nodes publish only after the agreed ordering/finality condition and signing step. A lagging or partitioned worker must catch up, forward, wait, or fail the request; it cannot claim to serve the current head or create an independent canonical fork.

The logical service also needs shared session/revocation semantics, consistent read watermarks, and resumable firehose cursors across node changes. Ordering mutations alone does not solve these service guarantees.

Canonical commit metadata and signed artifacts must be recoverable, so two workers serving the same revision return the same commit CID. Signer failover needs fencing to prevent competing publishers. These are open implementation problems.

05 / Identity and signing

A stable identity.
Distinct kinds of authority.

A handle names the user. A DID identifies the account. Login authority, repo signing, and DID rotation have different jobs.

Start with a normal did:plc, including an existing DID brought by migration. Prove the FID ↔ DID binding; retain standard ATProto client auth at the service boundary. No did:farcaster is proposed.

DID/PLC rotation authority is separate from the operational repo key. It authorizes identity updates such as changing the PDS endpoint or verification key. Farcaster/ETH-assisted recovery and rotation, wallet-only accounts, and passkeys remain research.

Many gateways do not mean many copies of a hot key.

Distributed repo signing is an open implementation problem. An initial proof can use one protected signer service, with explicit custody and access controls.

Signing research: threshold, delegation, and hardware protection

Longer-term candidates include threshold or distributed signing, delegated short-lived signing authority, secure/HSM-backed signing, and other compatible mechanisms.

These are research options, not established ATProto integrations. Delegation cannot assume consumers understand a new certificate chain or signature format.

Every externally visible repo commit must be a normal valid ATProto signed commit. Any signing arrangement must satisfy the accepted algorithm, key, encoding, and DID verification requirements.

06 / Account migration

Move your hosting.
Keep your identity.

The migration is from an ordinary PDS to the PurpleSky logical PDS. Moving between PurpleSky nodes should not be a migration at all.

A custom domain handle can continue resolving to the same DID. The DID’s PDS service endpoint changes to PurpleSky; the operational repo verification key can change as part of an authorized migration.

The user need not extract the old PDS’s private signing key. Import the repository and blobs, authorize the identity update using the applicable DID/PLC authority, then coordinate activation and deactivation so only one PDS is authoritative.

Preserving data and the exit path

Keeping the DID does not by itself copy content. Import and verify the repository, transfer blobs and relevant private preferences, and establish a shared bootstrap checkpoint from which every PurpleSky node can reconstruct. Retain custom-domain control and verify the handle binding.

Migration back to an ordinary PDS should retain the DID and repository too. Import/export, signing-key rotation, account cutover, and recovery when the old provider is unavailable remain prototype work.

Signed social operation
FarcasterATProto

Do not start here. Identity, signing, repository, and message semantics differ today.

Inside Level 2: what would be persisted?

Conceptual operations, not a defined Snapchain wire format:

create app.bsky.feed.post/abc
update app.bsky.actor.profile/self
create app.bsky.graph.follow/xyz
delete app.bsky.feed.post/old

The event envelope would need record content, stable keys, authorization, ordering, timestamps, and versioned projection rules. The adapter must first establish how the chosen network accepts and retains these operations.

Identical records can reproduce the MST root. Identical signed commits additionally require fixed commit metadata and a signing strategy or retained signed commit bytes. Replay alone does not recover private signing keys.

Pruning, deletion, snapshots, media availability, and migration need explicit policies before this can be a durable source of truth.

09 / The distributed proof

Write at A.
Rebuild at B. Verify anywhere.

All milestones proposed
  1. Authorize one user through an FID / Ethereum identity.
  2. Bind one ordinary did:plc.
  3. Submit a post through PurpleSky node A.
  4. Persist and order its mutation through Hypersnap/Snapchain.
  5. Start node B with empty local projection state.
  6. Have B reconstruct the current repo from shared state.
  7. Have B serve a valid com.atproto.sync.getRepo.
  8. Verify the result with an unmodified ATProto consumer.
  9. Submit a second mutation through B; have A serve the resulting head on the same canonical lineage.
The thesis to prove
Account state belongs to PurpleSky’s shared substrate, not to a PurpleSky machine.

If an unmodified ATProto relay/AppView can consume and verify a PurpleSky repository, the abstraction is working. The distributed proof additionally requires another node to recover and continue that same repository.

Begin by validating the substrate and a protected signer. Then cover profile, post, follow, updates/deletes, concurrent writes, retries, restart/replay, and com.atproto.sync.subscribeRepos resumption across nodes. Compare record CIDs, MST roots, revisions, and signed commit CIDs at the same publication watermark. Public AppView ingestion still depends on discovery and service policies.

10 / Open research

The interesting questions
are still open.

These are design decisions to investigate, not capabilities already delivered.

  1. What should be canonical: Snapchain mutations or ATProto blocks?
  2. How should an FID ↔ DID binding be represented and proven?
  3. How can protected or distributed signing preserve one canonical commit without copying hot keys to every node?
  4. Can repository reconstruction from Snapchain be fully deterministic?
  5. How should finality, concurrent writes, retries, read watermarks, and cross-node firehose resumption work?
  1. How much Farcaster-native data fits existing Lexicons directly?
  2. How can a new node reconstruct state after failures, pruning, or signer loss?
  3. Can an account migrate to an ordinary PDS while retaining its DID and repository?
  4. Could the same substrate expose both Farcaster-native and ATProto-native views?
  5. Which Hypersnap network, mutation format, and retention policy can support this?
